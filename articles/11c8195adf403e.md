こんにちは！[アルダグラム](https://aldagram.com/about/)でエンジニアをしている渡邊です。

2026年4月に Google から **Android CLI**（`android` コマンド）がリリースされました。
ターミナルから Android 開発を行うための公式 CLI で、AI エージェントから使われることも意識して設計されています。

リリースから半年ほどでコマンドがかなり増えて「結局何ができるの？」がわかりにくくなってきたので、この記事では **Android CLI でできることを一覧で把握できる** ようにまとめてみました。
また、普段 `adb` を使っている方向けに、**`adb` などの既存ツールとの違い** もあわせて紹介します。

:::message
この記事は **2026年11月時点の Android CLI v1.1.16919734** をもとにしています。
Android CLI は更新頻度が高いため、最新の情報は[公式ドキュメント](https://developer.android.com/tools/agents/android-cli)を確認してください。
:::

# インストールと初期設定

公式のインストールスクリプトでインストールできます。以下は Apple Silicon の Mac の例です。

```sh
curl -fsSL https://dl.google.com/android/cli/latest/darwin_arm64/install.sh | bash
```

他の OS 向けのスクリプトや、Homebrew・apt-get・winget などのパッケージマネージャーを使ったインストール方法は[ダウンロードページ](https://developer.android.com/tools/agents/android-cli/download)を参照してください。

インストール後は以下のコマンドで初期設定やアップデートを行います。

```sh
android init        # 設定・ディレクトリ・デフォルトのスキルをセットアップ
android update      # CLI 自体を最新版に更新
android completion  # シェル補完（Bash / Zsh）をインストール
android info        # SDK の場所などの環境情報を表示
```

# 環境・SDK 管理

## `android sdk`

`sdkmanager` の代わりになるコマンドです。

```sh
android sdk list --all                                     # インストール済み・利用可能なパッケージの一覧
android sdk install platforms/android-30@2 platforms/android-34  # バージョンを指定して複数インストール
android sdk update                                         # すべてのパッケージを最新に更新
android sdk remove <パッケージ名>                           # パッケージを削除
```

`--platform=linux_x86_64` のように指定すると、**ホストとは異なる OS・CPU 向けの SDK** を扱うこともできます。
また、複数のプロセスから同時に実行しても競合しないようにロックが取られるため、CI での利用にも向いています。

## `android auth`

`signals` やリモート実機など、Google のサービスを使う機能を利用する前に Google アカウントでログインします。

```sh
android auth login
android auth status
android auth logout
```

# プロジェクト作成・ビルド

## `android create`

テンプレートからプロジェクトを作成します。テンプレートは SDK から動的にダウンロードされるため、常に最新のテンプレートが使われます。

```sh
android create --list   # 利用できるテンプレートの一覧
android create empty-activity --name="My App" --output=./my-app
```

`--application-id`、`--namespace`、`--min-sdk` なども指定できます。

## `android build` / `android describe`

`android build` は **ビルド参照**（`[system://][path]?[target]`）を指定してビルドします。

```sh
android build :app
```

`:app` のようにバリアントを省略した場合は debug バリアントになります。

`android describe` はプロジェクトを解析し、ビルドターゲットや APK の出力先などを記述した JSON ファイルのパスを出力します。
AI エージェントや他のツールが「ビルドした APK がどこにあるか」を知るために使うことを想定したコマンドです。

# 実行・デプロイ

## `android run`

ビルド・インストール・起動を 1 コマンドで行います。

```sh
android run :app                                                # :app の debug バリアントをビルドして起動
android run --apks=app/build/outputs/apk/debug/app-debug.apk   # ビルド済みの APK を起動
android run --debug --activity=.ui.MainActivity --apks=app-debug.apk  # デバッガの接続を待って起動
```

`--type` を指定すると、Activity だけでなく Wear OS の `TILE` や `WATCH_FACE`、`COMPLICATION` なども起動できます。

## `android install`

起動はせず、インストールだけを行います。

```sh
android install :app
android install --apks=app/build/outputs/apk/debug/app-debug.apk
```

`android install` と `android run` は、デフォルトで **差分インストール（delta install）** を使います。
詳しくは後述の「adb との違い」で紹介します。

# エミュレータ・デバイス管理

## `android emulator`

AVD の作成（`create`）・一覧（`list`）・削除（`remove`）・起動（`start`）・停止（`stop`）を行えます。

```sh
android emulator list
android emulator start medium_phone
android emulator start --cold --headless medium_phone  # スナップショットを使わずに、ウィンドウなしで起動
```

`android emulator start` は **エミュレータの起動が完了して使える状態になってから** コマンドが終了します。
そのため、スクリプトで起動完了を待つための処理を自分で書く必要がありません。

## `android device`

- `android device hub`
  - 接続中の実機やエミュレータの画面をデスクトップのウィンドウにミラーリングし、そのまま操作できます
- `android device remote`
  - Google が提供するリモートの実機を予約して使えます
  - `projects` / `models` で使えるプロジェクトや機種を確認し、`create` で予約、`list` / `extend` / `remove` で予約を管理します
  - 予約した実機は `connect` で adb に接続されるため、`android run` などをローカルの端末と同じように使えます

:::message
リモート実機の利用料金は Google Cloud プロジェクトに請求されるため、別途料金がかかります。
:::

# UI の確認と操作

AI エージェントがアプリを操作するための中心となる機能です。

## `android layout`

画面の UI ツリーを JSON で取得します。

```sh
android layout --pretty
android layout --pretty --full --output=./hierarchy.json
```

各要素には `text`、`resource-id`、`content-desc`、`interactions`（`CLICKABLE` や `SCROLLABLE` など）、`bounds`、`center` などが含まれます。
デフォルトでは、テキストを持つ要素や操作できる要素だけが出力されます。すべての要素を出力したい場合は `--full` を指定します。

## `android input`

UI 要素を **セレクタ** で指定して操作します。

```sh
android input tap 'text=Submit'                                     # テキストで指定してタップ
android input tap 'id=submit_btn,class=Button,clickable=true'       # 複数の条件で指定
android input text 'user@example.com' 'id=email_input' --submit     # 入力して Enter
android input scroll 'id=recycler_view' --dir=down --until='text=Settings'  # 要素が出るまでスクロール
android input swipe 'id=card_view' --dir=left
android input key back                                              # 戻るボタン
```

セレクタは `text`、`id`、`class`、`desc` などのプロパティで指定でき、`txt=/^Var$/` のように正規表現も使えます。
結果は JSON で標準出力に出力されます。

## `android screen`

```sh
android screen capture -o screen.png             # スクリーンショットを保存
android screen capture --annotate -o screen.png  # UI 要素に番号付きの枠を描画して保存
android screen resolve --screenshot screen.png --string "#3"  # 番号 #3 の要素の中心座標を出力
```

`--annotate` は画像から UI 要素を検出して番号を振る機能です。
WebView など、`layout` では取得できない要素を操作したいときに使います。

# Compose プレビュー

## `android preview`

Jetpack Compose の `@Preview` を **端末も Android Studio もなしで** PNG に描画できます。

```sh
# @Preview 関数の一覧を表示
android preview list ':feature:calendar@devDebug'

# PNG を出力（--component-tree を付けるとコンポーネントツリーの JSON も出力）
android preview render ':feature:calendar@devDebug' \
  --fqn=com.example.feature.calendar.ScheduleColorItemKt.ScheduleColorItemPreview \
  --component-tree \
  --output=./preview
```

引数にはビルド参照を `モジュール@バリアント` の形式で渡します。
バリアントを省略すると `debug` が使われるため、product flavor を定義しているモジュールでは以下のようなエラーになります。
その場合は `@devDebug` のようにバリアントを明示します。

```
> Variant 'debug' does not exist in project ':feature:calendar'. Available variants: devDebug, devRelease, ...
```

弊社のアプリで試したところ、`list` で `@Preview` 関数の完全修飾名が一覧表示され、`render` で指定したプレビューの PNG が出力されました。
内部で Gradle のビルドが走るため、手元の環境では `list` に 1 分ほど、`render` に 40 秒ほどかかりました。

`--fqn` は複数指定できるほか、`--daemon` を付けるとレンダラーをバックグラウンドで常駐させられます。
UI の変更を AI エージェントに目で確認させたいときに便利そうです。

# Android Studio 連携

## `android studio`

起動中の Android Studio に接続して、IDE の機能をコマンドから使えます。

- `check`：起動中の Android Studio を確認
- `analyze-file`：ファイルを解析
- `find-declaration` / `find-usages`：シンボルの宣言・使用箇所を検索
- `open-file`：Android Studio でファイルを開く
- `render-compose-preview`：Compose のプレビューを描画
- `version-lookup`：Maven アーティファクトや SDK ツールの最新バージョンを検索

# 解析・計測

## `android analyze`

APK / AAB / AAR / JAR を解析し、パッケージ情報、DEX サイズ、R8 による縮小・最適化の指標、ライブラリの keep ルールに関する警告などを出力します。

```sh
android analyze app-release.aab
android analyze --format=json app-release.aab
```

## `android profiler`

- `systemtrace`：CPU スケジューリング、フレーム、GPU などを Perfetto のトレースとして記録
  - `--enable=compose.composition` や `--enable=compose.recomposition` を指定すると、Compose の再コンポーズとその原因となった State の読み書きまで記録できます（アプリ側に `androidx.compose.runtime:runtime-tracing` 1.13 以上が必要）
- `heapdump capture`：ヒープダンプを取得（`--type=hprof` は API 29 以上、`--type=perfetto` は API 31 以上）
- `session list` / `status` / `terminate`：プロファイリングのセッションを管理

## `android signals`

Firebase Crashlytics から本番環境のデータを取得します（事前に `android auth login` が必要です）。

- `context`：アクセスできるプロジェクトとアプリの一覧
- `crashes`：クラッシュ・ANR・non-fatal の一覧、絞り込み、内訳、サンプル
- `heaps`：OOM などのときに収集されたヒープダンプの一覧・詳細・ダウンロード

# AI エージェント向けの機能

## `android docs`

Android の公式ドキュメント（Android Knowledge Base）を検索・取得します。

```sh
android docs search "edge to edge"
android docs fetch kb://...
```

## `android skills`

AI エージェント向けの Android 公式スキルを管理します。Claude Code、Cursor、Cline、Windsurf など多くのエージェントに対応しています。

```sh
android skills find <キーワード>  # スキルを検索
android skills add <スキル ID>    # スキルをインストール
android skills list              # インストール済みのスキルの一覧
android skills update            # スキルを更新
android skills remove <スキル ID> # スキルを削除
```

## Journeys

**Journeys** は、ユーザー操作の流れを XML と自然言語で記述したテストです。

```xml
<journey name="My Journey">
  <description>A sample journey to illustrate the format</description>
  <actions>
    <action>Tap the "Home" icon</action>
    <action>Verify that the app is on its Home screen</action>
  </actions>
</journey>
```

AI エージェントが `layout`、`screen`、`input` などを使って各ステップを実行・検証し、結果をレポートとして出力します。

# adb との違い

ここからは、普段 `adb` を使っている方向けに違いを紹介します。

## 対応表

| やりたいこと | adb など | Android CLI | 違い |
|---|---|---|---|
| APK のインストール | `adb install` | `android install` | デフォルトで差分インストールになり、2 回目以降は変更分だけを送る |
| ビルドして起動 | `./gradlew installDebug` → `adb shell am start ...` | `android run :app` | 1 コマンドで完結する |
| UI ツリーの取得 | `adb shell uiautomator dump` → `adb pull` | `android layout` | JSON で直接出力され、操作できる要素に絞り込まれ、中心座標も含まれる |
| タップ・入力 | `adb shell input tap x y` | `android input tap 'text=Submit'` | 座標ではなくセレクタで要素を指定でき、要素の出現を待つこともできる |
| スクリーンショット | `adb exec-out screencap -p > a.png` | `android screen capture -o a.png` | ファイルに直接保存できる。UI 要素への番号付けもできる |
| エミュレータの起動 | `emulator -avd X` ＋起動待ち | `android emulator start X` | 起動完了までコマンドが待ってくれる |

## install の速度

`android install` と `android run` は、デフォルトで **差分インストール** を使います。
前回のデプロイから変更されたコードとリソースだけを端末に送るため、2 回目以降のインストールでは送信量が大幅に減ります。
リリースノートでは、差分インストールは adb より「桁違いに速い（orders of magnitude faster）」と紹介されています。

なお、差分インストールの恩恵を受けられるのは **2 回目以降のインストール** です。
また、`adb install` にも `--fastdeploy` や `--incremental` といった高速化のオプションはあるので、「何も設定しなくても差分インストールになる」点が大きな違いと言えそうです。

実際に弊社のアプリ（約 270MB の debug APK）で計測してみました。
同じ APK のまま、Android エミュレータと USB 接続の実機（どちらも API 33）にそれぞれ 3 回ずつ再インストールしています。

| コマンド | 端末に送ったサイズ | エミュレータ | 実機（USB 接続） |
|---|---|---|---|
| `adb install -r` | 268MB | 1.9〜2.3 秒 | 10.8〜11.4 秒 |
| `android install --use-delta-install=false` | 268MB | 3.0〜4.9 秒 | 11.7〜12.9 秒 |
| `android install`（差分インストール） | 7.4MB | 2.9〜4.9 秒 | 6.4〜8.2 秒 |

差分インストールでは、以下のように送信量が 97% 削減されていることがわかります。

```
Delta Install: Sent 7.41 MB patch instead of 268.34 MB (1 APK, 97.24% savings)
```

実機では、`adb install` の約 11 秒に対して差分インストールは 6〜8 秒ほどで、**3〜4 割ほど短縮** されました。
一方、エミュレータは PC 内で動いていて転送がボトルネックになりにくいため、所要時間は `adb install` のほうが短い結果になりました。
差分インストールの効果が出やすいのは、実機やリモート実機のように転送に時間がかかる環境だと言えそうです。

「桁違いに速い」とまではいきませんでしたが、APK のサイズや端末、接続方法によって結果は変わると思います。

なお、APK に変更がない場合でも、アプリを再起動させるために差分インストールが強制的に行われます。

```
Warning: APK is unchanged, but performing a forced delta reinstall to ensure the app restarts on device.
```

## adb が引き続き必要な場面

Android CLI は adb を置き換えるものではなく、adb と組み合わせて使うものです。
端末の指定には `adb devices` のシリアル番号を使いますし、リモート実機も adb に接続して使います。

以下のような操作は、現時点では Android CLI にコマンドがないため、引き続き adb を使います。

- `adb logcat`
- `adb shell`
- `adb push` / `adb pull`
- `adb forward` / `adb reverse`
- `adb uninstall`
- `adb shell pm grant` などのパッケージ操作

# 最後に

これからの開発では、AI エージェントがいかに開発しやすい環境を整えるかが重要になってくると考えています。
